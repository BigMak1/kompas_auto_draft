# Работа с ветками

## Кратко

Общие инструменты и личные материалы хранятся в `master`, учебный дизайн-документ —
в `ml-system-design`, эксперименты — в `ml-rnd`. Ветка `hw_1` сохраняет исходное
задание; новая работа по этому предмету ведётся в `ml-system-design`.

## Назначение веток

| Ветка | Что сюда относится |
|---|---|
| `master` | Общие скрипты `scripts/`, подключение к КОМПАС, настройки разработки и личные материалы |
| `ml-system-design` | `docs/ml_system_design_doc.md`, задания и пояснения по ML System Design |
| `ml-rnd` | `harness/`, `evaluation/`, их тесты, исследования метрик и описания опытов |
| `hw_1` | Историческая версия первого задания; существующие коммиты и ссылки сохраняются |

Все рабочие ветки содержат общую основу. Поэтому наличие `scripts/` в учебной ветке
нормально: эти скрипты нужны для её работы. Учебные материалы не требуется целиком
сливать в `master`.

## Переключение

Перед сменой ветки проверьте состояние и сохраните незавершённую работу в текущей ветке:

```bash
git status
git switch master
# или
git switch ml-system-design
# или
git switch ml-rnd
```

В каждой ветке README описывает именно её содержимое. Для нового домашнего задания
можно создать временную ветку от соответствующего предмета; pull request направляется
обратно в этот предмет, а не обязательно в `master`.

В `hw_1` отсутствуют новые правила игнорирования локальных настроек. Для чтения старого
задания удобнее открыть [ветку на GitHub](https://github.com/BigMak1/kompas_auto_draft/tree/hw_1)
или использовать `git show hw_1:docs/ml_system_design_doc.md`.

## Общие изменения

Правки общих инструментов оформляются отдельными коммитами в `master`.
Нужный общий коммит переносится в учебную ветку через `git cherry-pick <commit>`.
Так личные материалы из `master` и задания соседнего предмета не попадут туда случайно.
После переноса выполняются проверки соответствующей ветки.

Исправление экспериментального кода сначала остаётся в `ml-rnd`. Когда инструмент
становится общим, его переносят в `master` отдельно от данных и конкретных опытов.
История `hw_1` не переписывается, ветка не удаляется без отдельного решения владельца.

## Данные и локальное окружение

Репозиторий на GitHub публичный. Набор `kompas_data/e2e-27-v1/`, перенесённый из
общего проекта для внутренней работы, остаётся локальным вместе с его описью и хешами.
`runs/`, производные модели, `vendor/`, `mcp/`, `.mcp.json` и `.codex/` также
исключены из Git. Эти каталоги не переключаются вместе с веткой и требуют отдельного
резервного копирования; Git хранит только добавленные в него файлы.

Свежий клон `ml-rnd` содержит код и тесты, но для живых экспериментов нужно отдельно
восстановить разрешённые исходные данные, библиотеку КОМПАС и локальные настройки.
Ссылки на `runs/` и `kompas_data/e2e-27-v1/` в документации относятся к этим локальным файлам.
Существующие сырые результаты и исходные данные не правятся при переносе кода.

Репозиторий `kompas-drawings` остаётся самостоятельным командным проектом.
Изменения в нём оформляются отдельно; синхронизация репозиториев не выполняется автоматически.

## Проверки

В любой рабочей ветке: `uv run pre-commit run --all-files`.
В `ml-rnd` дополнительно выполняются тесты, описанные в её README.
Живой КОМПАС для локальных тестов не нужен; подключение и геометрия проверяются отдельными пробами.
Сообщения коммитов — короткие, на русском, с префиксом `feat:`, `fix:`, `docs:` или `chore:`.

# Модуль оценки

## Кратко

Основные показатели — IoU и F-score. Спецификация и ограничения — [METRICS.md](METRICS.md).
Офлайн-оценщик работает с сетками и нормализованными снимками измерений, результат
пересечения принимает из Windows-вычислителя КОМПАС. Общая команда готовит недостающие
входы через KsAPI, если вычислитель настроен и доступен. Готовый комплект позволяет
повторить оценку без КОМПАС. Зависимости находятся в отдельной группе `eval`.

## Запуск

Таск `uv run poe eval-geometry <папка прогона>` устанавливает группу `eval` и читает
`evaluation.json` из указанной папки. Повторяемые проверки — `uv run poe eval-geometry-test`,
синтетический прогон — `uv run poe eval-geometry-smoke`. Все таски имеют `help` в `pyproject.toml`.
Код завершения оценки 0 означает полноту основных метрик и проверок допуска,
2 — неполный основной результат либо ошибку. Вспомогательные показатели могут иметь пропуски.

По умолчанию команда выполняет полный цикл: проверку входов, недостающие выгрузки,
офлайн-совмещение и метрики поверхности, недостающие пересечения, итоговый отчёт.
Она подключается к **уже работающему** КОМПАС; второй экземпляр не запускает.
Если вычислитель недоступен, сохраняются доступные метрики и причины пропусков.
Отсутствие инфраструктуры не считается неудачной генерацией и не превращается в нулевой балл.

Отдельные режимы:

- `eval-geometry-offline <run>` или `eval-geometry <run> --offline` — без обращений к KsAPI/SSH;
- `eval-geometry-prepare <run>` — только сетки и Facts;
- `eval-geometry-inputs <run>` — проверка входов поверхности без изменения файлов.

Все имена выше — таски `uv run poe`. Проверка входов поверхности не подтверждает
готовность IoU: подходящий ответ пересечения определяется после совмещения.

## Вычислитель КОМПАС

`runner.py` и `readiness.py` не импортируют KsAPI. `pipeline.py` управляет этапами,
`backend.py` передаёт файловые задания, `kompas_worker.py` исполняет их на Windows
через `vendor/kompas_lib` и KsAPI. Windows-части нужна только стандартная библиотека Python
и обёртки установленного КОМПАС. NumPy, trimesh и остальные зависимости нужны оценщику.

На Windows без файла настроек используется `KOMPAS_BIN_DIR`. Для удалённой машины
передайте `--backend <settings.json>` или сохраните настройки в `evaluation/backend.json`
внутри прогона. Пример (пути и SSH-профиль заменить своими):

```json
{
  "transport": "ssh",
  "ssh_host": "windows-cad",
  "remote_repo": "C:\\work\\kompas-drawings",
  "python": "C:\\Python312\\python.exe",
  "bin_dir": "C:\\Program Files\\ASCON\\KOMPAS-3D v25 Study\\Bin",
  "timeout_seconds": 900
}
```

SSH-режим требует, чтобы `remote_repo` указывал на **ту же общую папку** репозитория,
видимую обеим машинам. Автоматическая отправка файлов на произвольный сервер пока
не реализована. Хеши кода вычислителя и vendor проверяются на обеих сторонах.
В локальном режиме нужны `transport: "local"` и `bin_dir`; `python` необязателен.
Настройки подключения не входят в задание метрик и не нужны для офлайн-повтора.

Проверяется фактическое подключение, версия v25 и единственный процесс из указанного
каталога. Рабочие модели копируются в новую папку задания. Открытые человеком документы
не закрываются, исходные M3D не сохраняются, активный документ восстанавливается.
Блокировка вычислителя допускает одну операцию за раз. После таймаута автоматического
повтора нет: удалённый процесс может ещё работать; сначала нужно проверить его состояние.

## Повторное использование выгрузок

`evaluation/pipeline_ГГГГ-ММ-ДД_ЧЧ-ММ-СС/` — журнал запуска оценки. Он создаётся
при каждом вызове, включая офлайн-повтор: `evaluation.json` хранит снимок настроек,
`preparation.json` — состояние входов, выполненные действия и путь к результату.
Новая папка `pipeline` сама по себе **не означает новую выгрузку**.
Совмещение, поверхностные и вспомогательные показатели пересчитываются при каждом
запуске; журнал позволяет связать этот расчёт с использованными входами.
В `preparation.json → actions` выгрузка отмечена полем `export`, булева операция —
`intersection`; пустой список означает, что новых таких операций не было.
`health` отдельно фиксирует проверку подключения. Готовые выгрузки и ответы пересечения
используются повторно; в офлайн-режиме обращений к КОМПАС нет.

Новые артефакты КОМПАС сохраняются в `evaluation/pipeline_…/worker/`, рядом с запросом,
ответом и логами. Экспорт содержит `model.stl`, `eval-facts.json`, `raw-facts.json`,
`export.json` и рабочую копию M3D. `kernel-facts.json`, `raw-facts.json` и
`export-source.json` сохраняют ответ вычислителя до нормализации; `normalize.py`
на стороне оценщика создаёт отдельный проверенный `eval-facts.json`.
`preparation.json` показывает, что использовано и что не удалось подготовить.

Исходный `evaluation.json` не изменяется. `evaluation/state.json` — атомарно обновляемый
указатель на подготовленные входы; пути в нём относительны папке прогона. При изменении
исходного задания он игнорируется. Переносить для офлайн-повтора нужно весь run,
включая исходные M3D, `state.json` и используемые папки артефактов.

Перед повторным использованием проверяются хеши M3D, сетки, Facts и сырых данных,
единицы, версия экспортёра и профиль триангуляции. Профиль можно задать в `evaluation.json`
полем `export`: `chord_mm` (по умолчанию 0.01), `angle` (0.05), `max_cells` (2000000).
Изменённые исходники или параметры требуют новой выгрузки. Старые результаты сохраняются.
Вручную подготовленные Facts без `export_manifest` поддерживаются как прежде;
их соответствие профилю триангуляции оценщик подтвердить не может.

Ответ пересечения используется только при совпадении хешей обеих моделей, сеток,
единиц и матрицы совмещения. Пересечение для другой позы повторно не используется.
Первый расчёт с новым пересечением сохраняет предварительный и итоговый отчёты;
после ответа КОМПАС обновляются только IoU, объёмные отклонения и сводные таблицы.
Совмещение, поверхность, диагностика и сопоставление размеров повторно не запускаются.
Итоговый манифест ссылается на предварительный отчёт через `reused_geometry`;
перед использованием проверяются хеши входов, отчёта и кода, а также настройки.
Повтор с готовыми ответами выполняет один офлайн-проход.

Расчёты для исходной позы и после совмещения, обоих направлений расстояний и разных
кандидатов ICP остаются отдельными операциями: это предусмотренные протоколом проверки.
Если файл `boolean-results.json` исчез, причина сохраняется в журнале как недоступный
кэш. При успешном восстановлении статус становится `restored`, и терминал сообщает
о восстановлении вместо прежней ошибки. Без КОМПАС недостающий IoU остаётся неполным.
Пути к действующим выгрузкам и пересечениям находятся в `evaluation/state.json`;
удаление указанных там папок требует повторной подготовки данных.

Обе команды оценки (`eval-geometry` и `eval-geometry-smoke`) показывают текущий этап
и прошедшее время: чтение входов, совмещение (номер положения ICP), метрики поверхности,
диагностика сетки и ожидание КОМПАС. Индикатор обновляется и во время долгого вызова;
общий процент не показывается, поскольку длительность этапов заранее неизвестна.
Прогресс выводится в `stderr`: в обычном терминале — одной обновляемой строкой,
при перенаправлении — отдельными строками при смене этапа и каждые 15 секунд.
`--quiet` отключает прогресс. После расчёта выводится краткая таблица:
основные IoU и F-score, выбранные вспомогательные показатели, средние, медианы и
число учтённых попыток. Рядом — VSR, IR, допуск F-score и путь к полному отчёту.
После таблиц выводятся сгруппированные причины пропусков и общее время прогона,
включая подготовку и ожидание КОМПАС. Это же время хранится в `preparation.json`
как `elapsed_seconds` и в итоговом `manifest.json → cost.total_seconds`.
`cost.seconds` относится к созданию конкретного отчёта; при повторном использовании
геометрии он включает только обновление объёмных показателей и запись результата.
Цвет показывает полноту расчёта, а не качество модели. Недоступный итог обозначается
тире; среднее только по измеренным попыткам не подменяет основной результат.

Метрики запускаются **последовательно**, а не отдельными параллельными заданиями.
F-score, CD, HD/HD95 и SIoU используют общие расстояния, поэтому в индикаторе сначала
показана подготовка расстояний, затем соответствующие группы показателей. Отдельно
видны нормали, связность/разрывы, самопересечения, ECD, МЦХ, топология, требования
чертежа и сопоставление каждого набора размеров: диаметры, линейные значения, радиусы,
резьбы. У размеров показаны номер группы и количество значений предсказания и эталона.
Потоки внутри численных библиотек возможны; оценщик сам метрики параллельно не запускает.

Строка «основные метрики рассчитаны» означает полноту IoU/F-score и проверок допуска,
а не наличие всех вспомогательных показателей. В частности:

- Ошибка размеров и выполнение требований требуют заполненного `requirements`
  с целями, допусками и измерениями по тем же идентификаторам. Общий список геометрических
  расстояний `dimensions_mm.linear` не является перечнем требований чертежа.
- ECD по B-rep требует экспортированных `edge_points` обеих моделей. Без них
  вычисляется отдельно обозначенное приближение по рёбрам сетки.
- Масса и массовые моменты сравниваются при подтверждённом одинаковом материале.
  Текущий экспортёр сохраняет числа МЦХ, но ещё не заполняет `material`; соответствующие
  сравнения остаются недоступными до расширения выгрузки. Геометрические объём и площадь
  от этого ограничения не зависят.

В [проверке KF0011 с итоговым временем](../../runs/e2e/kf0011-codex-005/evaluation/eval_2026-11-07_18-56-59/notes.md)
полный офлайн-проход занял около 207 с, из них около 169 с — сопоставление линейных
значений. Новых операций вычислителя не было; численные значения метрик совпали
с предыдущим итогом. Отдельная проверка финализации с сохранёнными ответами ядра
заняла около 0.09 с и дала побайтно тот же `metrics.json`, без повторного расчёта геометрии.

Параметры вывода: `--all-metrics` — все вспомогательные показатели,
`--no-color` — без цветов, `--quiet` — только путь к результатам, как раньше.
При перенаправлении в файл и при установленной `NO_COLOR` цвета отключаются автоматически.

Каждый расчёт создаёт **новую** папку `evaluation/eval_ГГГГ-ММ-ДД_ЧЧ-ММ-СС/` внутри входного
прогона, например `eval_2026-11-07_17-52-30`. Используется местное время машины,
на которой работает оценщик; время начала с часовым смещением записано в
`manifest.json → started_at`. Если имя занято запуском в ту же секунду, добавляется
номер `_2`, `_3` и далее. Прежние папки с микросекундами остаются на своих местах;
предыдущие измерения не перезаписываются. В папке лежат:

- `manifest.json` — версия протокола, хеши, настройки, версии библиотек и время;
- `metrics.json` — все показатели, статусы, знаменатели и матрицы;
- `report.md` — таблица с основными и вспомогательными метриками;
- `notes.md` — место для отдельной интерпретации результата;
- `raw/evaluation-input.json` — снимок входного задания;
- `raw/solid_requests.json` — задания вычислителю КОМПАС;
- `raw/<id>/deviations.json` — точки и расстояния для карты отклонений;
- `raw/boolean-results.json` — копия ответов ядра, если они переданы.

Тот же формат `<тип>_ГГГГ-ММ-ДД_ЧЧ-ММ-СС` используется для остальных новых папок:

| Тип | Назначение |
|---|---|
| `pipeline` | Журнал подготовки и расчёта |
| `mesh-probe` | Офлайн-диагностика сеток при поворотах |
| `probe` | Контрольная проверка в живом КОМПАС |
| `health`, `export`, `intersect` | Задания Windows-вычислителю внутри `worker` |
| `m2-synthetic` | Синтетический прогон метрик |

Имена создаёт общий `io.create_artifact_directory`, включая защиту от совпадения секунд.
Для новых разовых записей `import`, `launch`, `mesh-investigation` применяется тот же
помощник. Их исторические папки создавались вручную; постоянных команд, которые
автоматически создают их при каждом eval, нет.

Исходный прогон сохраняется по [общим правилам](../../tasks/README.md#формат-прогона),
со своим манифестом, исходной моделью и сырыми логами генерации.

## Задание на оценку

Минимальный пример `evaluation.json` (пути относительно его папки):

```json
{
  "purpose": "benchmark",
  "config": {"alignment": "rigid", "tau_relative": 0.01},
  "cases": [
    {
      "id": "shaft-078505",
      "family": "shaft",
      "tags": ["holes"],
      "generation_status": "success",
      "reference": {
        "mesh": "reference/model.stl", "units": "mm",
        "native": "reference/model.m3d", "facts": "reference/eval-facts.json"
      },
      "prediction": {
        "mesh": "generated/model.stl", "units": "mm",
        "native": "generated/model.m3d", "facts": "generated/eval-facts.json"
      },
      "requirements": [
        {"id": "hole-1-diameter", "kind": "dimension", "target": 8, "tolerance": 0.05, "unit": "mm"},
        {"id": "axes-parallelism", "kind": "constraint", "target": 0, "tolerance": 0.1, "unit": "deg"}
      ]
    }
  ]
}
```

Числа примера иллюстративны, не извлечены из чертежа вала.
Неудачная попытка записывается с `generation_status=failed|timeout|invalid` и без
`prediction`. Каждая ожидаемая попытка должна быть в списке. Поля `family` и `id`
обязательны; `id` уникален. Для разных числа тел/порогов используйте отдельные
протоколы запуска, а не подстройку конфигурации под отдельное предсказание.

## Снимок для оценки

`eval-facts.json` — **отдельный адаптер**, не новая версия контракта паспорта
и не утверждение, что текущие сырые ответы `kompas_lib` уже имеют этот формат.
Его нужно получить из R2 без переизмерения МЦХ по сетке. DTO описан в `models.Facts`:

| Поле | Смысл |
|---|---|
| `source`, `source_version` | `kompas`, точная версия источника |
| `mesh_sha256`, `native_sha256` | Привязка к сетке и исходному M3D |
| `mesh_units` | Единицы именно сетки; обязаны совпадать с заданием оценки |
| `units` | Только `mm`; объёмы мм³, площади мм², масса г |
| `solid_valid`, `body_count`, `volume_mm3` | Доказательство валидности твёрдого тела |
| `center_mm`, `principal_axes`, `principal_moments` | МЦХ для регистрации; оси — столбцы, моменты в том же порядке |
| `inertia_unit` | `mm5` для геометрических моментов либо `g_mm2` для массовых; при неизвестном значении моменты не сравниваются |
| `area_mm2`, `mass_g`, `material` | Дополнительные МЦХ; материал — стабильный идентификатор |
| `tree_fingerprint`, `document_fingerprint` | Подписи R2 для проверки копирования; должны быть содержательными |
| `topology` | Именованные неотрицательные счётчики, например `faces`, `edges` |
| `dimensions_mm` | Тип размера → список значений, с повторами |
| `measurements` | Заранее заданный id требования → измеренное значение в единицах этого требования |

При неизвестном значении — `null` или отсутствие необязательного поля; пустой словарь
измерений не означает выполненные требования. Сериализация всего сырого R2 остаётся
в его прогоне. Для МЦХ требуется единое соглашение о плотности и единицах моментов.
В `kompas_lib` некоторые вызовы возвращают объём в см³: адаптер обязан явно перевести
его в мм³; одного изменения имени поля недостаточно.

`edge_points` в описании модели — необязательный JSON-массив точек Nx3 на B-rep-кромках
в тех же единицах, что и mesh. Происхождение, равномерность по длине и seed обеспечивает
экспортёр; хеш файла сохраняется оценщиком. Без этих точек доступен только явно
обозначенный proxy ECD по резким рёбрам сетки.

Пропущенные подписи происхождения блокируют итоговый рейтинг. Совпадение хеша M3D,
подписи дерева либо подписи свойств отклоняет попытку согласно правилам репозитория;
одинаковый STL сам по себе не является доказательством копирования.

## Как подключить IoU к КОМПАС

Работа разбивается на два прохода, чтобы **один и тот же** результат регистрации
использовался и для поверхности, и для твёрдого тела:

1. Оценщик вычисляет матрицу и записывает `raw/solid_requests.json`.
2. Windows-вычислитель последовательно обрабатывает запросы, подключаясь через
   `ksapi.GetKompas()` к уже работающему КОМПАС v25 Study. Открывает копии исходных
   документов, помещает тела в собственный временный документ, применяет матрицу
   только к предсказанию. Тела уже в мм; масштабировать их второй раз нельзя.
3. Получает пересечение, проверяет успешность операции и измеряет объём **всех**
   результирующих тел. Разнесённые тела дают успешное пустое пересечение; неуспешный
   `Update()` даёт `status=error`. Оригинальные документы не сохраняются и не меняются.
4. Записывает ответ с тем же `request_sha256`. Общая команда сохраняет
   `boolean_results` в подготовленном задании. При ручном обмене файлами этот путь
   можно указать в исходном `evaluation.json`. Принимаются только совпадающие запросы.

В документации KsAPI v25 найдена цепочка для самой операции:
`IModelContainer.GetBooleans().Add()` → `SetBooleanType(ksIntersect)` → `SetBodies(...)`
→ `Update()`. Источник: справка `IBoolean`, пример из
`SDK/KsAPI/Samples/Examples/Source/IBoolean.cpp`, полученный через `ksapi-expert`.
Windows-реализация использует `ICopyGeometry`, `IBodyReposition` и `IBoolean`.
Она проверяет сохранение объёмов и соответствие габарита перемещённого тела сетке.
Первая версия поддерживает одну деталь с одним телом с каждой стороны. Расходящиеся
точные габариты дают доказанное пустое пересечение. При пересекающихся габаритах ошибка
`Update()` остаётся ошибкой, даже если причиной могло быть отсутствие общего объёма.

Форма успешного ответа (значения иллюстративны):

```json
{
  "request_sha256": "<SHA256 из запроса>",
  "backend": "kompas_v25",
  "backend_version": "<точная сборка>",
  "status": "ok",
  "prediction_volume_mm3": 1000.0,
  "reference_volume_mm3": 1000.0,
  "intersection_volume_mm3": 900.0
}
```

При сбое: `status=error`, `reason` с причиной, объёмы не выдаются как успешные.
Проверка запроса защищает от случайного смешения файлов и поз; это не криптографическое
доказательство честности внешнего исполнителя. Путь к файлу не заменяет проверку его SHA256.

## Границы реализации

Вычислитель снимает текущую сохранённую конфигурацию M3D; обход всех исполнений R2
не заменяет. Главные оси и моменты читаются из `IMassInertiaParam`. Если ядро возвращает
нулевые направления осей (обнаружено на кубе с равными моментами), адаптер диагонализирует
центральный тензор **из того же ответа ядра** и сверяет собственные значения с главными
моментами КОМПАС. Измерения по сетке для этого не используются. Способ получения осей
записывается в `export.json`; сырой ответ остаётся неизменным.
Размеры берутся из `measure_model`, ошибки дополнительного измерения сохраняются
в `raw-facts.json`. Материал, именованные инженерные требования и B-rep-точки кромок
автоматически пока не извлекаются: соответствующие показатели остаются недоступными
либо используют обозначенный proxy. Импорт STEP в этот путь не включён.

Опорная документация KsAPI v25: `IMassInertiaParam.GetAxisX` (фрагмент
`chk_73da1d5e8b238ce4ba7cbdf03ee7c6d1168ed146c5c31bf01b68f0fdb6a5f645`),
`GetJx0` (`chk_85c2d414018ab1094ad6bc5415efa297bbe1593a6438f7129f8be1201124d728`),
даты `IKompasDocument` (`chk_59c459bc10d08b48cc64e63bce579146ed950ac539c6fdfd59ce38535b551e36`).
Выгрузка и пересечение развивают подход из `kompas_auto_draft/evaluation/native_export.py`
и `native_boolean.py`; работа оценщика не требует соседнего репозитория.

`purpose=metric_validation` допускает тестовые аналитические факты и ответы и всегда
сохраняется в отчёте; `benchmark` такие источники отвергает.

## Живая проверка

Таск `eval-geometry-kompas-smoke <run> --backend <settings.json>` принимает контрольные
M3D-кубы из `<run>/inputs/`: prediction занимает [0,10] по всем осям, reference сдвинут
на 5 мм по X. Он проверяет МЦХ и итоговую топологию, поворот с переносом и пересечения.
Подтверждение в КОМПАС v25 Study, сборка 2780: [контрольный прогон](../../runs/m3/m3-kompas-controls-20261107-135029/notes.md),

Объём пересечения: 500 мм³ при частичном наложении, 1000 мм³ после совмещения поворотом
и переносом, 0 мм³ для разнесённых тел. Проверены объём 1000 мм³, площадь 600 мм²,
моменты в г·мм² и топология 6 граней / 12 рёбер / 8 вершин.

Счётчики снимаются с `IFeature(IBody)`, а не со всей детали: последняя включает
промежуточные объекты дерева. Опорный пример KsAPI:
`chk_de9ed5c302f9d5351f56b1bdcbf458dd75362fad1f970be5ee89bae31f3e76a8`.

На [KF0011, попытка 005](../../runs/e2e/kf0011-codex-005/evaluation/eval-20261107-140254-210652/notes.md)

полностью, офлайн-повтор не создавал заданий вычислителю. В протоколе 0.1.0 этот кейс
ошибочно блокировался проверками STL. Причина и исправление описаны ниже;
исторические отчёты сохранены без изменений.

## Численная диагностика STL

При выгрузке KF0011 общие вершины соседних треугольников получили различия порядка
`1e-14` мм. Загрузчик 0.1.0 объединял только точные совпадения и сообщал о разрывах.
Кроме того, PyMeshLab выдавал ложные самопересечения после поворота той же поверхности.
Это ошибки обработки и диагностики сетки, а не свидетельство повреждения исходной M3D.

В протоколе 0.2.0 загрузчик учитывает округление float64 с ограничением смещения
([правило](METRICS.md#валидность-и-диагностика-сетки)); в отчёт попадает
`inputs.*.mesh_normalization`. Для самопересечений используется libigl/CGAL
в режиме только обнаружения. Зависимость находится в группе `eval`;
используемый модуль `igl.copyleft.cgal` распространяется под GPL, как указано
в [документации библиотеки](https://libigl.github.io/libigl-python-bindings/).
Поверхность не перестраивается, исходный STL не перезаписывается.

[Проверка KF0011](../../runs/e2e/kf0011-codex-005/evaluation/mesh-probe-20261107-144441-490758/diagnostics.json)
показывает замкнутую сетку без самопересечений для обеих моделей в исходном положении
и после 24 поворотов с переносом. Максимальные смещения вершин составили
`3.40e-14` мм у эталона и `2.22e-16` мм у предсказания; вычисленные площадь и объём
сетки не изменились. Это не утверждение о совпадении формы с эталоном: за него
отвечают IoU, F-score и вспомогательные метрики.

Повторяемая диагностика без КОМПАС и без подбора совмещения:

```powershell
uv run poe eval-geometry-mesh-probe runs/e2e/kf0011-codex-005 --rotations 24
```

Новый каталог `evaluation/mesh-probe-…` содержит результаты, хеши исходников и версии
библиотек. Регрессионные тесты проверяют реальные щели, отверстия, пересечения тел
и перекрытия соседних треугольников. Недоступная проверка самопересечений блокирует
рейтинг, а не превращается в нулевую долю дефектов.

[Полный повтор KF0011 с протоколом 0.2.0](../../runs/e2e/kf0011-codex-005/evaluation/eval-20261107-144848-595368/report.md)
завершился с кодом 0: `rankable=true`, IoU ≈ 0.94973, F-score ≈ 0.98645
при допуске 1% диагонали эталона (≈ 1.039 мм). Пересечения пересчитаны в КОМПАС
для новых ключей протокола; исходные выгрузки использованы повторно.
Подробный [разбор причин](../../runs/e2e/kf0011-codex-005/evaluation/mesh-probe-20261107-144441-490758/investigation.md)
содержит ссылки на исходную ошибку и контрольные измерения.
